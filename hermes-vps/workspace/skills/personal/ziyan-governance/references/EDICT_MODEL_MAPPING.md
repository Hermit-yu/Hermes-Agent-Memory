# EDICT 模型映射（OpenClaw 会话与工作区治理）

## 1. 三省六部 → OpenClaw 治理对象映射

| EDICT 角色 | OpenClaw 场景映射 | 关键职责 | 落地优先级 |
|---|---|---|---|
| 中书省（规划） | 会话任务拆解、工作区改动计划生成 | 将用户请求拆成可执行步骤，标注风险级别 | 可立即落地 |
| 门下省（审核封驳） | 高风险动作前置审核（外发消息、批量改动、cron 变更） | 审核理由、允许/驳回、要求补充证据 | 可立即落地 |
| 尚书省（派发协调） | 工具调用编排与执行路由 | 按审批结果路由到 read/edit/exec/message 等工具 | 可立即落地 |
| 户部（资源） | 配额与成本（tokens、运行时资源） | 记录/限额、异常告警 | 中期 |
| 礼部（文档） | 规范模板与输出格式 | 统一审批单、变更单、审计报告模板 | 可立即落地 |
| 兵部（工程） | 工作区代码/脚本执行 | 仅在批准范围内执行改动 | 可立即落地 |
| 刑部（合规） | 安全红线、越权检测、审计取证 | 拦截危险命令/高风险外发、保留证据链 | 可立即落地 |
| 工部（基础设施） | 网关、自动化任务、部署变更 | 变更窗口与回滚方案 | 中期 |
| 早朝官（情报） | 日报与风险简报 | 汇总上一周期审批/驳回/异常 | 中期 |

## 2. 六大治理域映射

### 2.1 会话（Session）
- **中书省**：识别“普通问答 / 需审批动作”
- **门下省**：对高风险请求做显式批准
- **刑部**：会话内越权拦截（例如要求泄露敏感信息）

### 2.2 工作区（Workspace）
- **兵部**：执行文件改动
- **门下省**：批量改动（>N 文件）前置审批
- **工部**：涉及自动化脚本/运行链路的改动进入变更窗口

### 2.3 记忆（Memory）
- **礼部**：定义记忆写入格式与脱敏规范
- **刑部**：敏感字段禁止写入长期记忆
- **户部**：控制记忆体量与索引成本

### 2.4 工具权限（Tools）
- 分级：`read < edit/write < exec < message/send`
- **门下省**：对 `exec`（危险参数）和 `message/send`（外发）设审批闸门
- **尚书省**：审批通过后才允许工具调用

### 2.5 外发消息（Outbound）
- **门下省**：审批对象、内容、目标渠道
- **刑部**：敏感词/隐私泄漏检测
- **礼部**：输出模板化（减少误发）

### 2.6 审计（Audit）
- 必须可追溯：请求人、请求、审批人、结果、证据、执行日志、回滚点
- **刑部**主责，**早朝官**做周期汇总

## 3. 可立即落地 / 中期 / 不建议

## 可立即落地（1-2 周）
1. 高风险动作审批门（外发消息、批量文件改动、cron 变更）
2. 统一审批记录结构（JSON）+ 审计日志落盘
3. 工具权限最小化默认策略（deny-by-default for high-risk）

## 中期（1-2 月）
1. 角色化配额治理（token/调用频率/渠道）
2. 早朝简报自动汇总（每日审批与异常）
3. 变更窗口、双人复核、回滚自动化

## 不建议（当前阶段）
1. 过度官僚化：所有动作都审批（会严重拖慢交互）
2. 把“人格角色”硬编码进主链 runtime（应先在融合层验证）
3. 引入不可解释黑盒评分作为唯一放行条件

## 4. 结论

EDICT 在 OpenClaw 的最佳用法不是“复制朝廷设定”，而是把其 **分权 + 审核 + 可追溯** 机制抽象为治理层：在不污染主链的前提下，优先为高风险动作加审批闸门，再逐步扩展到配额、日报与回滚体系。
