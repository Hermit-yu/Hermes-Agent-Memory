# 工程框架：写项目的底层准则（编码 + 项目流程）

蒸馏自 KPanel 多智能体工程方法论（博客文章 + 仓库四份规范文档），**只保留架构思想与流程概念，不复制其代码、字段名、JSON shape 或文档措辞**（AGPL 边界，见末节）。具体项目再叠加自己的不变量层规则文件（云瞳见 `YUNTONG_RULES.md`，见 yuntong-product-governance skill）。

## When to Use
- 开新编码项目、写模块、改架构、重构、修 bug 前（先定不变量层 + 任务契约）。
- 形成任务卡、判断核验等级、出交付报告时。
- 代码评审、发版前门禁、部署/回滚、多智能体协作交接时。
- 不适用：纯聊天、一次性问答、无代码产出的任务。

## 三层结构（项目无关）

| 层 | 内容 | 放哪 |
| --- | --- | --- |
| 不变量层 | 产品性质、业务真源、信任边界、质量目标、存储选型、红线 | 项目内唯一规则文件（如 RULES.md），只此一份 |
| 流程层 | 任务契约、状态流转、核验分级、评审、交接、发布门禁 | 本 skill（通用）+ 项目 docs/tasks、docs/reviews 目录 |
| 验证层 | 门禁入口脚本、测试证据、验收记录 | 项目唯一 check 入口 + reviews 账本 |

同一规则只在最高适配层定义一次，下层引用不复制；冲突时以不变量层为准。改规则文件时同步复核入口脚本与文档是否仍一致。（延伸：方法论/流程/架构类准则默认放在跨项目底层 skill，别锁进某个项目的 skill；只有业务真源、红线、具体路径这类项目专属不变量才下沉到项目内 RULES 文件。）

## 任务契约（写码前）
每个非琐碎任务开工前先写清：

```
目标与非目标：一句话说清做什么、明确不做什么
允许/禁止路径：本次可动的文件目录，禁碰的边界
事实来源：真实状态在哪（不靠会话记忆、不靠旧报告）
基线与回滚：精确 commit SHA + 回滚点
核验等级：L0-L3 + 验收命令
权限边界：本地提交 / 推送 / 部署 / 发布，哪些被授权
```

Definition of Ready（未满足不开写）：目标明确、真源已确认、工作树干净且基线精确、验证等级与证据类型清楚、会改变方案的悬而未决项已问用户（纯实现细节可最小假设并记录）。

## 风险与核验分级 L0-L3

| 级 | 适用 | 必做核验 |
| --- | --- | --- |
| L0 | 文档 / 文案 / 注释 | diff 检查 + 链接/格式 |
| L1 | 单模块、单页面、无跨层契约变化 | 编译/单测/构建；界面变更补错误态 |
| L2 | 跨层契约、鉴权、安装/部署脚本、写路径 | L1 + 集成 + 失败注入（非法输入/缺凭据）+ 回滚验证 + 真机验证 |
| L3 | 版本发布、一键安装、生产部署 | 全量门禁 + canary + 回滚点记录 + 验收记录 |

- 核验与改动风险匹配：小改动不跑发布全链，也不许用局部测试冒充 L2/L3 门禁。
- 每个门禁只留**一个权威入口**（单一脚本/Make 目标）；文档与 CI 只引用，不写参数不同的平行实现。
- 可自动验证的硬规则进测试/静态检查；暂时不能自动化的必须写明需要的证据，不靠"人工注意"。

## 编码纪律

1. 最小、可验证、可回滚的改动；不夹带无关重构；保留他人未提交修改，遇未知脏改动保留现场先问归属。
2. 行为变化必补测试；兼容结论必须注明证据。
3. 结构化 API：用户输入禁止拼接进 shell 命令；SQL 参数化。
4. 存储选型：JSON = 小型有界状态（原子写 tmp+rename、条数上限）；JSONL = 有界追加历史（行数/轮转上限）；SQLite = 出现事务/索引/结构化查询/增长压力才上。禁止无界增长、长期双写双真源。
5. 写宿主机/配置的路径：原子写入 → 语法检查 → 备份 → 失败即回滚；长任务状态可恢复，不留半份中间态。
6. 日志与审计脱敏密钥；下载/依赖来源做完整性校验。
7. 派生视图必须是采集层算好的字段；消费端不得拿原始字段做假过滤（分类判定放在有上下文的那一层，传下去一层就还原不回来了）。
8. 持久化读写两侧的 shape 契约要对齐，测试必须含"带存量数据重启读回"的往返；只新建不读回的套件对读侧 bug 结构性盲区。
9. 模板占位符渲染后必须用样例参数校验（预览/审计/执行共用同一渲染结果）；入库前把各模板全渲染一遍目检。
10. 采集/探测类改动 oracle 差分看不见（fixture 喂字符串对），必须用真实探针单验；采集节奏先实测再定测试窗口。多层聚合采集（firewall 式 ufw+iptables+… 能采几层采几层）与消费端解析必须同形：拼接带层标记文本、消费端按 marker 偏移切块解析——`^` 锚点正则只匹配物理行首，对以 `\n\n` 拼接的块文本会漏掉首层之后的全部标记；用 `PREG_OFFSET_CAPTURE`/字节偏移切块，且没采到的层显式标注、消费端跳过不猜（误报红线）。验证存储文本内容时用字节计数（`LENGTH-LENGTH(REPLACE(x,CHAR(10),''))` 等），别信 CLI/od 肉眼看 `\n`（非交互输出把真换行转义成字面两字符，曾因此误判真 bug）（WHY：肉眼判读会把转义假阳性当数据缺陷，浪费整轮排查）。
11. UI 可读性基线：有语义文字最小 12px，正文/可操作控件 14px，辅助信息 13px；对比度 ≥4.5:1；支持 200% 缩放不裁切；状态反馈不只靠颜色（文字/图标/结构同时表达）；层级不靠缩小字号实现。
12. 用户可见文案面向最终使用者：口语化、去术语、不裸露后端枚举字面量；确需可追溯时在显示层保留原值（如「正常（ok）」），未知值回退原值。改文案只动显示措辞，不碰后端枚举/数据（属 L1，不改契约）。
13. 一个渲染函数常被多条数据路径喂不同 shape（SSE 实时帧 vs REST 快照兜底 vs 首屏加载）——按“由哪条路径保证存在”的那个判别字段分支，缺字段的分支给诚实的“还没建立/还在连”提示，别假设单一 shape 也不硬填默认值；渲染前先把每条路径的真实字段名对到权威真源（API 响应 struct 的 `json:` tag，不是磁盘落盘文件、不是会话记忆）。
14. 重写**已能用的功能视图/模块**前，先确认 git 基线是可运行的功能版并保留它；说明/文案类改动只**追加**，不覆盖数据绑定与路由。误覆盖了立刻 `git checkout -- <被覆盖文件>` 恢复功能版再重建，别在覆盖后的空壳上继续堆（WHY：覆盖会把真实数据绑定丢成静态壳，后续越堆越偏离基线，且无法回退到"能用的那版"）。
15. **前端/SPA 交付必须真浏览器端到端验证**，"构建成功 + 页面返回 200" 不证明渲染了内容；黑屏常见根因 = App 用了 `<router-view>` 但 main.js 没注册 router，或视图被覆盖成壳。排查/恢复/断言 recipe 见 `references/frontend-delivery-verification.md`。
16. **数据生产/消费两端要键名对齐并用合成数据单测**：新增 上下文/DTO 构建器 → 规则/评估函数/渲染器 这类数据对时，消费端读键 = 生产端写键，先对真源核对一遍；再用合成输入单测正反两类（应触发值 / 不应触发值 / 缺数据 data_gap）。E2E 里"阈值没超所以没发现"是**假绿**——管线断在键名/解析层时 E2E 照样全绿，看不见（本次实况：ctx 写 `disk`、规则读 `disk_pct`，磁盘 95% 不触发，8 个合成用例才抓出）。
17. **心跳/离线/新鲜度阈值 ≥ 1.5× 实际上报周期**再定（agent 每 2 分钟推 → 在线窗口 180s、离线判 300s），否则在线状态在每个上报边界来回闪；"每资产取最新"的聚合查询要过滤到可用行（如 `WHERE metrics_status='collected'`），否则最新一条垃圾行（unavailable/failed）盖住真数据，显示成"无数据"。

## 评审：双臂 + 独立

- 六维固定矩阵（约束臂逐维过，每维给 通过/缺口/不适用+依据）：① 正确性 ② 信任边界（鉴权/注入/路径穿越/脱敏）③ 资源上限（无界查询/增长/并发）④ 失败与回滚 ⑤ 可观测性 ⑥ 证据诚实性。
- **双臂必做**：约束臂 = 按清单逐文件 100% 覆盖改动文件；自由臂 = 不受清单限制盲跑（接口不一致、隐含假设、生命周期竞态、吞异常）。自由臂先跑并落盘；只计自由臂之外新增且经核对成立的发现为有效产出，单跑约束臂不得宣称已评审。
- **独立性**：评审者 ≠ 实现者；干净上下文独立复核（子代理/干净会话/另一模型），不可得时如实记录限制。
- finding 严重度：阻断 / 重要 / 一般 / 建议；处置：open / fixed-and-tested / refuted / duplicate / accepted-risk。修复走正常任务流，评审本身不改代码。评审记录进账本（基线 SHA、范围、双臂发现数、复核方式），findings 详情独立落盘。
- 报告禁用"应该没问题"：每个维度只许四态——已验证（精确提交+环境+命令+原始结果）/ 已实现未实机验证 / 未实现 / 不适用（写依据）。

## 交接与多智能体纪律

1. 交出前原写者停止写入；完成的任务必须已形成本地候选提交 + 工作树 clean；阻塞任务如实记录未提交文件，不冒充完成。
2. 交接包固定字段：精确提交、分支、基线、已验证事实、未验证风险、回滚点、推送/发布状态。接手方重新 fetch 核对远端状态后才声明接手；默认新工作树，不复用对方脏树。
3. 状态真源 = 远端分支/提交/门禁结果/发布记录；会话记忆与聊天记录不是真源，只用于协调恢复。
4. 并行写任务物理隔离（专用分支/worktree，一分支一任务）；同一资源同一时刻唯一写者；发布窗口独占。

## 多代理编排运行模式（主编审 / 编码 / 独立复核）

适用：用户指定多个子代理协作的长编码任务，或要求「随时看进度 / 防偷懒 / 定期汇报」时。

1. **三角色分工**：主编审（我）只定契约、出 M0 审计、汇总签核，不亲自写码；编码子代理按契约实现；复核子代理在干净上下文独立挑错。三个代理结果全部汇到主编审，主编审签核才算该里程碑过——主编审既当裁判又当运动员会自我放水。
2. **交接门禁（关键）**：子代理自述「已提交 / 已验证 / 已修好」不是事实。交接时主编审亲自重跑 `git log`（确认独立 commit 真存在，别把基线 commit 当成交付点）+ 现场 live 探活（curl 目标端点读真实状态码）后再交复核。子代理报「200」但现场是 000/500 的，一律打回、不得沿用其数字（WHY：子代理常把临时起的服务、未真正落地的 commit 当成已通过，直接信就会放行假成功）。
3. **长任务进度纪律**：建一份里程碑看板文件 + 一个只读进度探子脚本（每次输出 git / 新产物 / 各代理 live 日志尾）；按用户指定周期（未指定默认 15 分钟）挂一个定时自动汇报，数据源 = 看板 + git + 各子代理 live 日志，只陈述读到的事实、读不到的写「未见」，禁止空话；某代理日志停滞 > 20 分钟或报错要单独标红。配方（看板结构 / 探子脚本 / 定时汇报 prompt / 交接核对清单）见 `references/multi-agent-progress.md`。

## 修 bug 与提交门禁实战规则

适用：修生产 bug、清数据残留、验证后需要提交的场景（本次：host 去重护栏 + DB 残留清理 + verify 幂等 + agent-token 吊销验证 → 全批提交）。

- **数据层先清残留，再修代码**：DB 里同 host 重复卡（#3-#6）必须先删，再在 API 层加去重护栏（409 拒重），否则修代码后旧残留仍污染列表（WHY：代码只防新插入，已有重复必须手动清）。清时保留用户真实资产（#2 reached），仅删测试残留。
- **幂等验证优先于代码修改**：verify.sh / 测试脚本每次跑前先 GET 查现有资产再决定 POST；已有则复用 id，避免每次验收都新建——这才是根因（WHY：脚本自身非幂等是重复污染的主因，API 护栏只是第二道）。
- **token / 权限类修复要验证完整链路**：吊销路由（update revoked_at）+ 推送鉴权（revoked_at IS NULL）必须双侧核对，不能只看路由代码；吊销后真实 curl 目标端点确认 401，才算生效。
- **提交前必须：git diff --stat 确认无意外污染 + DB 现场验证（残留已清 / 只留预期行）+ 用户明确授权（"全批 允许提交" 不默认推断，必须拿到）**；未经授权或现场未验证的改动不得提交（WHY：未验证提交 = 把假成功写进基线，后续回滚点失效）。提交 message 需含修的内容 + 提交范围（文件数 / 行数 / 新文件），便于后续 `git log --oneline` 即知交付点。
- **工作树与 DB 状态要同步记录**：提交后立刻 `git rev-parse --short HEAD` + 现场 DB 复查（如 `SELECT id,host,status FROM server_asset WHERE host='local';`），把提交 SHA 和数据状态写入同一句话，不靠记忆（WHY：后续子代理常把基线 commit 当交付点，只有精确 SHA + 现场数据才能分辨）。
- 检查清单与命令序列见 `references/bug-fix-commit-checklist.md`。

## 发布与部署（L3）

- 候选冻结：门禁全绿后锁定精确候选 + 回滚点；冻结后任何代码变化 = 新候选，重跑受影响门禁，旧结果不得沿用。
- 部署预检放非生产环境做（身份/运行时/端口/磁盘/架构）；上生产后不许现场拼新命令或首次引入未预检工具。
- canary 用真实业务端点（health/登录），不用进程存活信号（进程常先于端口 bind，会误判绿）。
- 回滚点双侧保留：旧版本产物 + 数据备份；回滚可达性验证通过才算完成。
- 验收记录逐条写：候选身份、命令、环境、证据、未验证项、回滚方法；"测试全过"不得替代业务/真机结论；前一层通过不自动证明后一层成功。

## 诚实交付（汇报纪律）

- 只陈述执行过的命令与看到的结果；失败如实报，替代方案说清取舍；计划与推测不当成功上报。
- 工具退出码 ≠ 业务成功；"未验证"不是丢脸，比无法复查的"应该没问题"更有价值。
- **骨架/桩 ≠ 交付**：空函数签名 + 注释描述意图、"前端已构建"但内容区黑屏，都算**未完成**，只能报成"骨架/桩"，不得报成"完整可用"。判定一个功能模块已交付 = 已路由 + 已数据绑定到数据源 + 真实浏览器里渲染出实时数据 + 你实际跑过它；缺任何一项就如实写"骨架/桩，待接入"。反复被用户指"其实没落地"是最高频失误——别用"已写完/已同步/构建通过"冒充"可用"。
- 交付报告固定收尾：候选提交 / 本次范围 / 已验证 / 未验证 / 回滚点 / 推送-发布状态。

## 新项目实例化步骤

1. 写不变量层规则文件（产品性质/业务真源/信任边界/质量目标/存储选型/红线），全项目唯一入口。
2. 建 `docs/tasks/`（任务卡 + 模板）与 `docs/reviews/`（账本 + findings 目录）。
3. 写变更感知 check 入口（单脚本分级 L0-L3），本地与发布共用同一入口。
4. 登记验证环境（哪些真机可用、哪些禁用）与依赖固定版本策略。
5. 任务按契约流程走：契约 → DoR → 实现 → 分级自验 → 双臂独立评审 → 候选提交 → L3 发布。

## 重建 / 全量重写流程（本次云瞳 / KPanel 借鉴 实际验证过）

适用：删旧部署 → 重写后端 → 重写前端 → 重新上线。参考 `references/rebuild-checklist.md`。

- 数据层先清残留，再修代码护栏（DB 重复 host / 测试残留 / 旧 token 先手动清，再加 API 409 去重）；清时保留真实资产，记录 SELECT 现场。
- 先完整读参考源码（KPanel `cmd/paneld` + `internal/` 或旧版 `api/public/index.php`）再动手，反对直接在 `/root` 写新文件 —— 真实源码在 `/opt/yuntong/` 及 `/workspace/kpanel-source/`，改时直接编辑源文件或在 `/workspace/` 目录新建，不写 `/root/` 新文件。
