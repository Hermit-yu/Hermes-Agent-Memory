# 修 bug → 提交 门禁检查清单（可复用）

配套 SKILL.md「修 bug 与提交门禁实战规则」。适用：生产 bug 修复、数据残留清理、验证后需要提交。

## 顺序（不要打乱）

1. DB 现场查：确认残留形状（`SELECT id,host,status FROM server_asset WHERE host='local';`）→ 记录真正存在的行数。
2. 清残留（保留用户真实资产，删测试残留）→ 再查确认只留预期行。
3. 代码修：API 层加去重护栏（404/409 拒重）或修逻辑；不夹带无关重构。
4. 幂等验证：verify.sh / 测试脚本先 GET 查现有再决定 POST；真实 curl 目标端点确认状态码（200/401/409）。
5. 双侧核对（token/鉴权类）：路由代码 + 实际推送鉴权必须都验证；吊销后确认 401。
6. 提交前检查：`git diff --stat` 无意外污染；DB 现场复查已清/只留预期；用户明确授权（"全批 允许提交" 不能推断）。
7. 提交：message 含修内容 + 范围（文件数/行数/新文件）；`git rev-parse --short HEAD` 记录。
8. 提交后同步记录：提交 SHA + DB 状态写入同一句话（不靠记忆），便于后续子代理分辨基线 vs 交付点。

## 机制（WHY 记一句）

- 先清数据再修代码：代码只防新插入，旧残留必须手动清，否则修完仍污染列表。
- 幂等优先于护栏：脚本自身非幂等是根因，API 护栏是第二道。
- 提交前必须用户授权 + 现场验证：未经验证提交 = 假成功写进基线，回滚点失效。
